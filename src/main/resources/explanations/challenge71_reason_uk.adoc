= Розкриття секрету конфігурації Dev Container

*Чому жорстке кодування секретів у Dev Container є критичним ризиком безпеки*

Dev Container — це спільні середовища розробки, які налаштовуються через `.devcontainer/devcontainer.json`. Оскільки ці файли зазвичай відстежуються в системі керування версіями, жорстке кодування секретів у визначеннях devcontainer створює кілька загроз безпеки:

1. **Розкриття для всіх читачів репозиторію**: Будь-хто з доступом на читання до вихідного репозиторію (або публічних форків і клонів у проєктах з відкритим кодом) може прочитати секрети, зашиті в `.devcontainer/devcontainer.json`.
2. **Витік змінних середовища**: Облікові дані, визначені в `containerEnv` або `remoteEnv`, впроваджуються в кожен процес усередині контейнера, тому будь-який скрипт, дочірній процес або діагностичний інструмент у контейнері має до них доступ.
3. **Залишаються в історії Git**: Після коміту видалення секрету потребує перезапису історії git, а застарілі ключі часто залишаються дійсними необмежено, якщо ротацію не виконано.
4. **Важче виявити**: Багато інструментів перевірки секретів і контейнерів досі не знаходять `devcontainer.json`, оскільки він поводиться інакше, ніж `Dockerfile`.

*Усунення та найкращі практики:*

- **Використовуйте GitHub Codespaces Secrets / VS Code Dev Container Secrets**: Впроваджуйте секрети динамічно через секрети репозиторію/користувача Codespaces або налаштування VS Code, а не зашивайте їх у файлах конфігурації.
- **Використовуйте підміну локального середовища**: Динамічно посилайтеся на змінні середовища хоста в `devcontainer.json` за допомогою синтаксису `${localEnv:MY_SECRET}`.
- **Використовуйте файли `.env` із `.gitignore`**: Зберігайте секрети розробки в локальних файлах `.env`, які явно виключені з керування версіями у `.gitignore`.
- **Застосовуйте рішення для керування секретами**: Отримуйте секрети під час виконання за допомогою спеціалізованих менеджерів секретів (напр., HashiCorp Vault, AWS Secrets Manager, Azure Key Vault, GCP Secret Manager).
