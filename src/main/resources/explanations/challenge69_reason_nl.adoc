*Waarom je een geheim nooit in een agent-skill moet stoppen*

Een skill is gebouwd om te worden gedeeld. Dat is het hele punt: je schrijft de workflow één keer en elke developer, agent en CI-job gebruikt hem opnieuw. Dit betekent dat een geheim in een skill de slechtst mogelijke eigenschappen heeft:

- Het wordt gekopieerd naar elke machine die de skill installeert, inclusief persoonlijke laptops.
- Het belandt in de repository, dus het staat voor altijd in de git-geschiedenis, ook nadat je het hebt "verwijderd", waardoor je het geheim moet roteren.
- Het wordt gepubliceerd op skill-marketplaces en registries, waar het wordt geïndexeerd en doorzoekbaar is.
- Het wordt door de agent gelezen en kan daardoor worden teruggekaatst in chattranscripts, logs en telemetry die van derden zijn.
- Het is een *gedeelde* referentie, dus die wordt bijna nooit geroteerd en bijna nooit ingeperkt.

----
Wat je in plaats daarvan moet doen:

- Houd referenties buiten de skill en laat de skill ze uit de omgeving lezen, bijvoorbeeld `$STAGING_DEPLOY_TOKEN`.
- Documenteer *welke* variabele nodig is en *waar* je die kunt ophalen, nooit de waarde zelf.
- Geef elke consument zijn eigen kortlevende referentie met de minste bevoegdheden in plaats van één gedeelde teamtoken.
- Scan skill-bestanden met een secretscanner in pre-commit en CI, net zoals je broncode scant.
- Behandel een geheim dat ooit in een skill heeft gezeten als gecompromitteerd en roteer het.
----

[NOTE]
====
Skills, regels, prompts, MCP-serverconfiguraties en agent-instructiebestanden zijn allemaal code als het om je secretbeheer gaat. Als je een token niet in een `.java`-bestand zou hardcoden, doe dat dan ook niet in een `SKILL.md`.
====
