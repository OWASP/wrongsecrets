*Чому використання коду для розміщення секретів — погана ідея.*

Як бачите, ми отримали трохи більше гнучкості, ніж у випадку з challenge1. Однак: у нас все ще є пароль у коді!

Хоча тепер ми можемо легко перевантажити змінні на пізнішому етапі — як ви можете побачити в наступних завданнях, ми часто бачимо, що секрети зберігаються як частина конфігурації Spring Config або Spring Cloud, без перевизначення їх на пізнішому етапі. Це означає, що кожен, хто має доступ до конфігурації Spring Cloud, тепер може дізнатися, що це за секрет.

Використання розподіленого рішення, такого як https://cloud.spring.io/spring-cloud-config/reference/html/[Spring Cloud Config], де ви керуєте властивостями своєї програми зовні, може мати таку ж проблему, якщо ви не будете обережні. Уважно перегляньте розділ https://cloud.spring.io/spring-cloud-config/reference/html/#_security[security], перш ніж використовувати Spring Cloud Config.

Що робити замість цього:
- Не зберігайте секрети у відкритому тексті у властивостях програми або репозиторіях конфігурації. Отримайте їх з менеджера секретів під час розгортання або виконання.
- Якщо Spring Cloud Config має обробляти секрети, спробуйте впровадити їх через безпечні шаблони, використовуючи менеджери секретів як джерела (наприклад, впровадити секрет за допомогою контейнера сховища). Якщо це неможливо: увімкніть підтримуване Spring Cloud шифрування та автентифікацію, обмежте доступ до авторизованих робочих навантажень та операторів, а також проведіть аудит доступу.
