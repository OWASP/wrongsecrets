= Exposition des secrets de configuration du conteneur de développement

*Pourquoi le codage en dur des secrets dans les conteneurs de développement représente un risque de sécurité critique*

Les conteneurs de développement sont des environnements de développement partagés configurés via `.devcontainer/devcontainer.json`. Ces fichiers étant généralement suivis par un système de contrôle de version, l'intégration directe de secrets dans les définitions des conteneurs de développement présente plusieurs risques de sécurité :

1. **Exposition à tous les lecteurs du dépôt** : Toute personne ayant un accès en lecture au dépôt source (ou aux forks et clones publics dans les projets open-source) peut lire les secrets codés en dur dans `.devcontainer/devcontainer.json`.
2. **Fuite de variables d'environnement** : Les informations d'identification définies dans `containerEnv` ou `remoteEnv` sont injectées dans chaque processus à l'intérieur du conteneur, les rendant accessibles à tout script, processus enfant ou outil de diagnostic exécuté dans le conteneur.
3. **Persistance dans l'historique Git** : Une fois validé, la suppression du secret nécessite des réécritures de l'historique Git, et les clés obsolètes restent souvent valides indéfiniment si aucune rotation n'est effectuée.
4. **Plus difficile à détecter** : De nombreux inspecteurs de secrets et de conteneurs ne détectent toujours pas le `devcontainer.json` car il se comporte différemment d'un `Dockerfile`.

*Mesures correctives et meilleures pratiques :*

- **Utilisez les secrets GitHub Codespaces / les secrets du conteneur de développement VS Code** : injectez les secrets dynamiquement via les secrets du dépôt/utilisateur Codespaces ou les paramètres VS Code plutôt que de les coder en dur dans les fichiers de configuration.
- **Utilisez la substitution d'environnement local** : Référencez dynamiquement les variables d'environnement de l'hôte dans `devcontainer.json` en utilisant la syntaxe `${localEnv:MY_SECRET}`.
- **Utilisez les fichiers `.env` avec `.gitignore`** : Placez les secrets de développement dans des fichiers `.env` locaux qui sont explicitement exclus du contrôle de version dans `.gitignore`.
- **Adoptez des solutions de gestion des secrets** : récupérez les secrets lors de l’exécution à l’aide de gestionnaires de secrets dédiés (par exemple, HashiCorp Vault, AWS Secrets Manager, Azure Key Vault, GCP Secret Manager).
