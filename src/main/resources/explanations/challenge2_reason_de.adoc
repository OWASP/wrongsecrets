*Warum es eine schlechte Idee ist, Geheimnisse im Code zu speichern.*

Wie du siehst, haben wir etwas mehr Flexibilität als bei Herausforderung 1. Allerdings: Das Passwort ist weiterhin im Code enthalten!

Obwohl wir die Variablen später problemlos überschreiben können – wie du in den nächsten Aufgaben sehen wirst – werden Geheimnisse häufig in der Spring- oder Spring-Cloud-Konfiguration gespeichert, ohne sie später zu überschreiben. Das bedeutet, dass jeder mit Zugriff auf die Spring-Cloud-Konfiguration das Geheimnis erfahren kann.

Die Verwendung einer verteilten Lösung wie https://cloud.spring.io/spring-cloud-config/reference/html/[Spring Cloud Config], bei der du die Eigenschaften deiner Anwendung extern verwaltest, kann bei unvorsichtiger Vorgehensweise zu demselben Problem führen. Lies daher vor der Verwendung von Spring Cloud Config unbedingt den Abschnitt „Sicherheit“ unter https://cloud.spring.io/spring-cloud-config/reference/html/#_security[security] durch.

Was du stattdessen tun solltest:
- Bewahre keine Geheimnisse im Klartext in Anwendungsproperties oder Konfigurationsrepositories auf. Rufe sie bei der Bereitstellung oder zur Laufzeit aus einem Secrets Manager ab.
- Falls Spring Cloud Config Geheimnisse verwalten muss, injiziere diese nach Möglichkeit über sichere Muster mit Secrets Managern als Quelle (z. B. ein Geheimnis über einen Vault-Sidecar-Container). Falls das nicht möglich ist: Aktiviere die von Spring Cloud unterstützte Verschlüsselung und Authentifizierung, schränke den Zugriff auf autorisierte Workloads und Bediener ein und überwache den Zugriff.
