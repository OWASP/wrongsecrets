*Warum ein Skill-Bundle die gleiche Überprüfung benötigt wie Ihr Quellcode*

Ein Skill-Bundle ist ausgelieferte Software. Es enthält ausführbare Skripte, läuft auf Entwicklerrechnern und in CI-Umgebungen und wird von Personen installiert, die es nicht selbst geschrieben haben. Es als „einfach nur etwas Markdown-Code“ zu behandeln, führt dazu, dass Geheimnisse in großem Umfang verbreitet werden.

Bei dieser Herausforderung häufen sich zwei Fehler:

- Das Token ist im Bundle enthalten, sodass jeder, der den Skill installiert, über funktionierende, gemeinsam genutzte Anmeldeinformationen verfügt.
- Wenn Sie den Skill innerhalb von Claude teilen, hat jeder mit Zugriff auf den Skill Zugriff auf das Geheimnis.
- Das Token ist Base64-kodiert, was eine Kodierung und keine Verschlüsselung darstellt. Es verhindert, dass ein einfacher Geheimnisscanner ausgelöst wird, und schützt auch sonst niemanden. Jeder, der das Paket besitzt, kann es mit einem einzigen Befehl entschlüsseln.

Der zweite Punkt ist der gefährlichere der beiden, denn er wandelt ein erkennbares Problem in ein nicht erkennbares um. Der Scanner meldet keine Meldungen mehr, der Befund verschwindet aus dem Bearbeitungsprotokoll, und die Berechtigung bleibt jahrelang gültig.

----
Was Sie stattdessen tun sollten:

- Die Anmeldeinformationen werden zur Laufzeit aus der Umgebung oder einem Geheimnismanager gelesen. Fehlen diese, wird ein deutlicher Fehler mit einer klaren Fehlermeldung ausgegeben.
- Korrigieren Sie niemals die Ergebnisse eines Geheimnisscanners, indem Sie den Wert verschlüsseln, aufteilen oder verschleiern. Korrigieren Sie ihn, indem Sie das Geheimnis entfernen und es rotieren lassen.
- Überprüfen Sie jede Datei in einem Skill-Bundle, nicht nur die `SKILL.md`. Skripte, Referenzdokumente und Beispielkonfigurationen sind allesamt Teil der Angriffsfläche.
- Überprüfen Sie das Bundle in der CI: Entpacken Sie es und führen Sie Ihren Secret Scanner über den extrahierten Inhalt aus, einschließlich eines Base64-fähigen Regelsatzes.
- Veröffentlichen Sie Bundles aus einer Build-Pipeline, die von vornherein keinen Zugriff auf Produktivzugangsdaten hat.
----

[NOTE]
====
Kodierung ist keine Sicherheitsmaßnahme. Wenn das Einzige, was einen Angreifer von Ihren Anmeldeinformationen trennt, ein `base64 -d` ist, sind die Anmeldeinformationen öffentlich.
====
