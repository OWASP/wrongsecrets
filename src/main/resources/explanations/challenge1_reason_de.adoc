*Warum es eine schlechte Idee ist, Geheimnisse im Code zu speichern.*

Sie merken es sicher schon: Viele Geheimnisse lassen sich leicht im Code aufspüren. Selbst nach der Kompilierung kann man den Code per Reverse Engineering analysieren und das Geheimnis finden. Deshalb sind fest codierte Geheimnisse niemals ratsam. Oftmals unterliegen wir dem Irrglauben, dass ein Angreifer den Code nicht entschlüsseln kann, wenn wir es selbst nicht können. Daher glauben viele, dass fest codierte Geheimnisse in C/C++/Go sicherer sind als in Java. Allen, die das denken: Dekompilieren Sie eine Anwendung mit Tools wie https://ghidra-sre.org/[*Ghidra*].

Die Geheimhaltung eines im Code verankerten Geheimnisses ist eine Sache. Eine andere Herausforderung ist die Offenheit: Jeder, der Zugriff auf den Code und/oder die kompilierten Dateien hat, kann das Geheimnis erfahren. Erschwerend kommt hinzu: Verlässt der Entwickler, der das Geheimnis fest im Code verankert hat, das Unternehmen, kennt er es möglicherweise, da es weiterhin im Code gespeichert ist! Ebenso wird das Geheimnis kompromittiert, wenn Code oder Dateien durchsickern, und ein Austausch wird schwierig. Und mal ehrlich: Wissen Sie nach ein paar Jahren noch, wo dieses Passwort liegt?

Was Sie stattdessen tun sollten:
- Halten Sie Geheimnisse aus dem Quellcode und den kompilierten Artefakten. Rufen Sie sie zur Laufzeit über einen Secrets Manager oder über eine Workload-Identity mit eng begrenztem Zugriff ab.
- Durchsuchen Sie Repositories und Build-Artefakte nach Geheimnissen und rotieren Sie alle Zugangsdaten, die committet oder ausgeliefert wurden.
