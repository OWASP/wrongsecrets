*Warum du niemals ein Geheimnis in einer Agent-Skill ablegen solltest*

Eine Skill ist zum Teilen gebaut. Das ist der ganze Sinn dahinter: Du schreibst den Workflow einmal und jeder Entwickler, jeder Agent und jeder CI-Job nutzt ihn wieder. Das bedeutet: Ein Geheimnis in einer Skill hat die denkbar schlechtesten Eigenschaften:

- Es wird auf jede Maschine kopiert, auf der die Skill installiert wird, einschließlich persönlicher Laptops.
- Es landet im Repository und ist damit für immer in der Git-Historie, auch nachdem du es „entfernt“ hast – du musst das Geheimnis also rotieren.
- Es wird auf Skill-Marktplätzen und in Registries veröffentlicht, wo es indexiert und durchsuchbar ist.
- Es wird vom Agenten gelesen und kann so in Chat-Transkripte, Logs und Telemetrie Dritter geraten.
- Es ist eine *geteilte* Credential und wird deshalb fast nie rotiert und fast nie eingeschränkt.

----
Was du stattdessen tun solltest:

- Halte Credentials aus der Skill heraus und lass die Skill sie aus der Umgebung lesen, zum Beispiel `$STAGING_DEPLOY_TOKEN`.
- Dokumentiere, *welche* Variable gebraucht wird und *wo* man sie bekommt, niemals den Wert selbst.
- Gib jedem Verbraucher eine eigene kurzlebige Credential mit den geringsten Rechten statt eines gemeinsamen Team-Tokens.
- Scanne Skill-Dateien mit einem Secret-Scanner in pre-commit und CI, ganz wie du Quellcode scannst.
- Behandle ein Geheimnis, das jemals in einer Skill stand, als kompromittiert und rotiere es.
----

[NOTE]
====
Skills, Regeln, Prompts, MCP-Server-Konfigurationen und Agent-Instruktionsdateien sind alles Code, was dein Secret-Management betrifft. Wenn du ein Token nicht in einer `.java`-Datei hartcodieren würdest, hartcodiere es auch nicht in einer `SKILL.md`.
====
