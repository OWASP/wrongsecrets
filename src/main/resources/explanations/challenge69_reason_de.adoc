*Warum Sie niemals ein Geheimnis in einem Agent-Skill ablegen sollten*

Ein Skill ist zur gemeinsamen Nutzung konzipiert. Genau das ist ihr Sinn: Man schreibt den Workflow einmal, und jeder Entwickler, Agent und CI-Job verwendet ihn wieder. Das bedeutet, dass ein Geheimnis in einem Skill die denkbar schlechtesten Eigenschaften besitzt:

- Es wird auf jeden Rechner kopiert, auf dem der Skill installiert ist, einschließlich persönlicher Laptops.
- Es landet im Repository und bleibt somit für immer in der Git-Historie erhalten, selbst nachdem man es "entfernt", was einen zwingt, das Geheimnis zu rotieren.
- Es wird auf Skill-Marktplätzen und in Registries veröffentlicht, wo es indexiert und durchsuchbar ist.
- Es wird vom Agenten gelesen und kann daher in Chatprotokollen, Logs und Telemetriedaten von Drittanbietern wiedergegeben werden.
- Es handelt sich um eine *gemeinsame* Anmeldeinformation, daher wird sie fast nie rotiert und fast nie eingeschränkt.

----
Was Sie stattdessen tun sollten:

- Halten Sie Credentials aus dem Skill heraus und lassen Sie den Skill diese aus der Umgebung lesen, zum Beispiel `$STAGING_DEPLOY_TOKEN`.
- Dokumentieren Sie, *welche* Variable benötigt wird und *wo* man sie erhält, niemals den Wert selbst.
- Jedem Verbraucher sollte ein eigenes, kurzlebiges Berechtigungszertifikat mit minimalen Berechtigungen anstelle eines gemeinsamen Team-Tokens zugewiesen werden.
- Scannen Sie Skill-Dateien mit einem Secret Scanner in Pre-Commit und CI, genau wie Sie Quellcode scannen.
- Behandeln Sie ein Geheimnis, das jemals in einem Skill aufgetaucht ist, als kompromittiert und rotieren Sie es.
----

[NOTE]
====
Skills, Regeln, Prompts, MCP-Serverkonfigurationen und Agenten-Anweisungsdateien sind allesamt Code, was Ihre Geheimnisverwaltung betrifft. Wenn Sie ein Token nicht in einer `.java`-Datei fest codieren würden, sollten Sie es auch nicht in einer `SKILL.md`-Datei fest codieren.
====
